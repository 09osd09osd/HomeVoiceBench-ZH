# 全量运行的任务调度

内容推理和评分标准不变，仅调整执行顺序以减少等待。以下是离线测评调度，不代表实时语音交互延迟。

1. 输入文本16并发，输入TTS/质检24个在途任务。遇到实测限流后，TTS新请求间隔约1.05秒。已验证的相同波形按哈希复用。
2. 单块GPU依次运行Qwen 2B、Qwen 4B、Edge，客户端并发8、4、8。ASR批量16，级联TTS从12按实测显存余量增长到最多32。用于评分补充证据的输出ASR按实际WAV时长、再按SHA256排序，减少长短音频混批的填充；记录在output_asr_effective.batch_order中。基线输入ASR和三组已经产生的回答不变。
3. 实际回答音频一旦可用，就进入24路听音初评，不等全部推理结束。
4. 全量运行期间新增8路后续评分工作器，每份初评保存后立即使用原有固定语义复核；有预定分歧时按原协议重新听音。最多24路初评加8路后续评分。提示哈希、温度、首个结构有效答案规则和客观硬约束均未改变。
5. 后续评分工作器用文件修改时间跳过未改变的记录；同一记录先复核、后裁定，由一个工作器顺序保存。最终批处理会等待其心跳结束，复用匹配证据的结果，避免重复请求或覆盖。
6. 闭集数字检查在输出ASR全部完成后统一执行。已有听音裁定与其数值判断保留，其余需要核验的记录按同一协议处理。

实际阶段墙钟、批量成员、batch seed、资源重试、请求用量和评分来源都保存。输入预热与补齐的耗时见 benchmark/reports/input_audio_preparation_history.json；不能把最后一次缓存补齐的36.75秒当作全部语音生成耗时。后续评分调度见 benchmark/reports/scoring_followup_stream.json。

此调度不重试模型答错、不选择较好的回答，也不更改正式数据与评分协议。它增加的是阶段重叠，不能凭工作器数量直接宣称加速倍数。

本轮后续评分工作器在 `qwen35_2b/C13_011` 遇到连续四次非规范JSON响应后停止，失败状态单独保留。格式恢复增加了字段类型提醒，将所有系统通用的格式尝试上限扩为八次；第五次得到首个有效结构，采用其失败结论，没有选择较高分。评分提示、原音频、温度和token预算未改变；此前无效响应全部保留。剩余复核由正常批处理补齐，最终完整性检查逐题确认评分齐全。详见 `benchmark/reports/scoring_format_recovery.json`。
